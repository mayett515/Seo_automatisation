## ADR 0021 Command-Offer Prerequisite: Release Plan Target CAS

- Added a DB-managed non-negative `page_versions.row_version`; inserts are forced to revision zero, every update advances it, and callers cannot forge revisions.
- Replaced release-plan id-only input with a strict unique target set carrying each displayed page-version status and row version.
- Release-plan creation locks project-owned page versions in stable id order, re-reads current state, applies a pure stale-first admission decision, and writes draft plan/item truth only when every target still matches and remains approved with approval evidence.
- Page versions remain the terminal class in the established release lock order. Creation does not acquire an existing release-plan lock after taking target locks.
- The Page preview submits the displayed revision and invalidates page-version queries after conflicts so stale UI state self-heals.
- Contract/domain tests pin the closed request and decision taxonomy. Real-PostgreSQL coverage pins insert/update revision ownership and a forced lifecycle-update versus planning lock interleaving with zero plan/item writes for the stale loser.
- This slice creates no report command offers, consent receipts, or dispatch rows. Both initial target-CAS prerequisites are now implemented; consequential report action truth remains the next separate slice.

## Release Page-Version Lock Ordering Follow-Up

- Closed the reviewed pre-existing sorted-versus-unsorted page-version lock seam without changing lifecycle behavior.
- Deploy approval now deduplicates and sorts release target ids before locking and projecting them to `release_candidate`.
- Release planning canonicalizes contract-valid UUID text before sorting, keeping JavaScript request ordering aligned with PostgreSQL `uuid` ordering even for uppercase input.
- The shared release-candidate demotion helper materializes its target set, locks page versions in ascending id order, and only then restores them to `approved`. Cancellation, re-preflight, deploy failure, verification failure, and rollback all reuse that helper.
- Real-PostgreSQL coverage holds the higher page-version lock, proves cancellation already owns the lower row while waiting, then releases both writers and verifies both versions are restored.
