# 2026-08-25 - TypeScript schema and architecture review

Scope: repository rules, product and architecture documentation, TypeScript
contracts, domain logic, API and worker shells, adapters, persistence, and the
main frontend flows. This is a structural review, not a feature implementation.

## Product understanding

The product is a Local SEO Mission Control implemented as a modular monolith.
It imports website, Search Console, tracking, SERP, and field evidence; turns
that evidence into opportunities and page proposals; lets a human constrain,
edit, and approve page content; and only then hands mutations to deterministic
workers. Deployment verification establishes live truth, and customer reports
may claim only facts bound to persisted evidence and verified artifacts.

The governing lifecycle is coherent across documentation and code:

```text
evidence -> research -> proposal -> constrained editing -> approval
         -> preflight -> deploy -> verify -> evidence-bound report
```

AI is deliberately confined to scouting, reasoning, drafting, and explanation.
Contracts validate, people approve, workers perform effects, and verification
decides what is actually live. That separation is the architecture's strongest
property.

This is not a codebase suffering from widespread TypeScript overengineering.
Most of the apparently heavy schemas encode real audit, authorization,
publication, or recovery constraints. The more important issues are a few
unfinished boundaries that fabricate state, local-demo assumptions leaking
into authenticated UI, and broad implementation files whose capabilities have
become independently nameable.

## Prioritized findings

### 1. High - authenticated navigation is pinned to `demo-project`

**Evidence:** `apps/web/src/router.tsx:81-109` builds authenticated navigation
links with the literal `demo-project`. Several screens independently fall back
to the same value, including `apps/web/src/screens/gsc-connect.tsx:78-79`,
`tracking-keys.tsx:147-148`, `performance-dashboard.tsx:107-108`, and
`project-dashboard.tsx:170-171`.

**Why it matters:** the production backend correctly requires a real,
tenant-authorized project identifier. The shell can therefore navigate an
authenticated user away from the selected project and into a value the API
must reject. Repeating the fallback in individual screens also creates several
sources of routing truth.

**Smallest change:** make the typed project route parameter or selected-project
route context own navigation. Permit `demo-project` only when the existing
local-scaffold UI flag explicitly allows it. A new global project store is not
needed if the route already owns the state.

### 2. High - release reads fabricate a draft release

**Evidence:** `apps/api/src/modules/releases.module.ts:347-359` returns a parsed
draft `ReleasePlan` when persistence is unavailable or the identifier is not
valid.

**Why it matters:** callers cannot distinguish a real persisted draft from a
synthetic object. That contradicts the project's state-honesty rule and is
particularly dangerous in a lifecycle where approval, deploy, rollback, and
verification depend on durable truth.

**Smallest change:** reject invalid identifiers at ingress, preserve the
not-found behavior for a missing persisted release, and fail closed when
required persistence is unavailable. If a dry-run mode is a product
requirement, model it as an explicit discriminated response variant rather than
impersonating a persisted release.

### 3. High - release notes expose placeholder data despite having a table

**Evidence:** `apps/api/src/modules/releases.module.ts:875-893` returns a fixed
placeholder release note. The `release_notes` table exists in
`packages/db/src/schema/releases.ts:82`, but no production read or write owns
it. The deployment rules require release notes to be persisted separately.

**Why it matters:** an API that appears operational returns invented customer-
visible data, while the documented persistence boundary is unused.

**Smallest change:** read persisted notes and return an empty collection when
none exist. If note generation is intentionally deferred, expose that state
explicitly; do not return sample content from a production endpoint.

### 4. Medium - website fact extraction is too narrow and too eager

**Evidence:** `packages/domain/src/index.ts:244-280` contains a fixed service
vocabulary and area stop-word list. Service extraction iterates only that list
at `packages/domain/src/index.ts:512-534`; area extraction at lines `537-576`
can treat arbitrary non-stop-word route segments such as `blog` or `impressum`
as locations.

**Why it matters:** the product is meant to support different local-service
sectors. The current logic can both miss legitimate services and manufacture
location facts, polluting later opportunity research. Human confirmation
limits the blast radius but does not make the candidate evidence reliable.

**Smallest change:** inject a project- or sector-owned service vocabulary into
the pure extraction function, require a location route pattern or corroborating
page text, and return `unknown`/unclassified candidates when evidence is weak.
Keep the decision pure; no service class is needed.

### 5. Medium - `ReleasesService` has earned an internal capability split

**Evidence:** `apps/api/src/modules/releases.module.ts` contains planning,
reading, preflight, approval, cancellation, deployment handoff, rollback,
verification, notes, rollback-point reads, and persistence helpers in one hot
file. The main methods span roughly lines `158-1066`; the file has also had high
recent churn.

**Why it matters:** these are now independently nameable capabilities with
different permissions, actors, transaction roots, and external effects. The
module remains one valid bounded context, but policy ownership is harder to
locate and review than in the recently decomposed Pages and Reports modules.

**Smallest change:** preserve `ReleasesService` as the Nest-facing facade and
extract planning, preflight/approval, execution handoff, and rollback/
verification capabilities around one aggregate store that owns lock ordering
and persistence. Do not introduce a generic workflow engine.

### 6. Medium - the AI package index owns three separate capabilities

**Evidence:** `packages/ai/src/index.ts` combines opportunity scouting (from
about line `97`), page proposal generation (from about `407`), and section-copy
suggestions (from about `468`) through a file exceeding 1,400 physical lines.

**Why it matters:** each capability has distinct prompts, validation, fallback,
and business vocabulary. The large index makes changes and ownership harder to
scan even though the public package boundary is sound.

**Smallest change:** move the implementations to `opportunity-scout.ts`,
`page-proposal.ts`, and `section-copy.ts`, leaving `index.ts` as the compatible
barrel. This is a file-level cohesion change, not a new package or class layer.

### 7. Medium-low - `SiteHostingPort` advertises unused legacy operations

**Evidence:** `packages/adapters/src/index.ts:271-278` exposes `createDeploy`
and `restoreDeploy` alongside the operations used by workers. Production code
uses the begin/upload/status/publish/rollback path; `createDeploy` is exercised
only by its adapter test, and `restoreDeploy` has no caller.

**Why it matters:** this is genuine interface overengineering: the port claims
capabilities the application does not need, increasing adapter and test surface
while making the intended deployment protocol less obvious.

**Smallest change:** confirm there are no external consumers, then remove the
unused methods, implementations, types, and isolated tests. Split the adapter
source by purpose if desired, retaining a barrel for compatibility.

### 8. Low - recovery failure input permits invalid optional combinations

**Evidence:** `packages/db/src/opportunity-research-execution.ts:453-465`
declares `expectedRecoveryCount`, `staleBefore`, and `expectedExecutionEpoch`
as independent optional properties. A later guarded branch still needs
`input.staleBefore as Date` around line `548`.

**Why it matters:** the function's valid call modes are a small closed set, but
the type admits partial recovery preconditions and then repairs that ambiguity
at runtime.

**Smallest change:** use a discriminated input or a nested optional recovery
object whose required fields occur together. The cast should disappear as a
consequence.

### 9. Low - tracking list response is duplicated in the frontend

**Evidence:** `apps/web/src/screens/tracking-keys.tsx:14-36` hand-writes
`TrackingKeyListResponse` and a custom parser. The shared contract already owns
`TrackingKeySummarySchema` in `packages/contracts/src/tracking.ts:61-79`, but
not the list envelope.

**Why it matters:** one transport shape now has separate frontend and backend
interpretations, contrary to the otherwise consistent schema-derived contract
strategy.

**Smallest change:** add a strict `TrackingKeyListResponseSchema` to contracts,
derive its output type, and parse the API response with it in the frontend.

### 10. Low - queue audit input weakens a closed job vocabulary to `string`

**Evidence:** `apps/api/src/queue-producer.ts:31-39` declares the audit
`type` as `string`, while `packages/contracts/src/jobs.ts:17-37` and around line
`251` already own the closed `JobType` vocabulary.

**Why it matters:** typos and unsupported job names can enter an audit record
without a compile-time failure.

**Smallest change:** import and use `JobType`. Add a trigger-source union only
if that vocabulary is already stable; do not create one speculatively.

## Type-system assessment

### Especially good types

- `packages/contracts/src/pages.ts:120` models content and decorative media as
  a discriminated union, making invalid alternative-text combinations
  unrepresentable.
- `packages/contracts/src/pages.ts:157-304` combines strict `PageJson`, bounded
  sections, unique identifiers, command unions, and action-conditional approval
  checks. These types protect a real publication boundary.
- `packages/contracts/src/report.ts:289-319` models claims and navigation
  references explicitly, then validates evidence, claim, and action references
  across the complete projection. The complexity is justified by immutable,
  customer-visible audit truth.
- `packages/contracts/src/opportunity-research.ts:508-528` distinguishes
  candidate evidence from stored evidence and keeps axes and evidence keys
  exact. This makes research output useful to deterministic downstream logic.
- `packages/domain/src/page-studio.ts:39-84` and
  `packages/domain/src/work-recovery.ts:14-33` use small decision unions for
  expected outcomes. Shells can perform effects without hiding policy in
  controllers or workers.
- `packages/contracts/src/releases.ts:6-47` deliberately separates release
  plan, provider operation, deployment, and verification state. Those are not
  duplicate status fields: they are separate truths required to avoid calling
  provider success “live.”
- Database enums in `packages/db/src/schema/pages.ts:27-33` and
  `packages/db/src/schema/releases.ts:18-26` derive from contract vocabularies
  instead of mirroring string literals.
- `packages/config/src/index.ts:25-109` validates both field shapes and
  cross-field operational timing constraints, while production configuration
  fails closed.

Across the contract package, external types are normally derived from Zod via
`z.output`; there is no broad pattern of parallel schema and interface
definitions. This is one of the cleanest parts of the repository.

### Complex but not overengineered

- Report projections, digest binding, canonicalization, and publication
  transitions are heavy because customer-visible claims must be reproducible.
- Opportunity Research evidence ledgers and portfolio axes are substantial but
  encode the product's core differentiator rather than framework ceremony.
- The multiple release status models reflect distinct authorities and failure
  domains.
- Pages and Reports facade services contain delegation, but the facades preserve
  a stable application boundary while capability classes own policy and
  transactions. That split is justified.
- The page registry is large, but it owns one coherent concern: validating and
  rendering the canonical `PageJson` source of truth. An internal file split
  may improve navigation; a new architectural layer would not.
- The work-recovery strategy map has seven meaningful variants, so a typed map
  is earned. Per-lane source files may become useful if it grows further, but
  the state model itself is not excessive.

### Actually overengineered or unnecessarily broad

- The unused `SiteHostingPort` operations are the clearest unearned abstraction
  surface.
- Large `index.ts` implementation files in AI and adapters obscure ownership;
  this is organization debt, not a reason for more runtime abstractions.
- There is no evidence that the repository needs a Result library, pattern-
  matching library, generic workflow framework, or more service classes. Plain
  TypeScript is serving the domain well.

## Readability and coherence

Naming is consistently domain-oriented: proposal, evidence, preflight,
verification, rollback point, report projection, and recovery decision mean the
same things in docs and code. Pure decision functions are usually easier to
read than the shells calling them, and comments normally explain invariants
rather than syntax.

The main readability cost comes from a few 1,000-1,500-line implementation
files (`releases.module.ts`, AI `index.ts`, deploy/report/recovery workers, and
the page registry). Size alone is not a design failure: the worker handlers own
deep effect protocols and the page registry owns one cohesive representation.
Extraction should follow independently nameable capabilities and ownership,
not a line-count threshold. Releases and AI meet that test today; the generic
deploy and report handlers do not yet justify a new framework.

## Recommended order

1. Remove the `demo-project` production path and stop release endpoints from
   fabricating state.
2. Implement or explicitly defer persisted release notes.
3. Improve website fact extraction before expanding sector coverage or relying
   more heavily on automated opportunity discovery.
4. Split Releases and AI internally while preserving public facades and package
   imports.
5. Apply the three small type cleanups: recovery input union, shared tracking
   list schema, and `JobType` audit input.
6. Remove unused hosting-port operations after consumer confirmation.
